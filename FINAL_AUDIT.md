# Финальный аудит безопасности и надёжности NovaMind-v2

## Итог

Внесены и протестированы существенные hardening-изменения в API, OAuth/CSRF, работе с файлами и медиа, поиске, terminal policy, админских действиях и тестовой изоляции. Это снижает выявленные риски, но **проект пока нельзя считать production-ready**: остаются отсутствие настоящего OS/container sandbox, неполная пользовательская идентичность и отсутствие распределённой инфраструктуры для задач и хранения.

Работа находится локально в ветке `agent/production-hardening`, HEAD `868df79`. Изменения не закоммичены и не отправлены; merge/deploy и изменения GitHub secrets не выполнялись. PR #12 не затрагивался. `examples/turtle_spin/spin.gif` не менялся.

## Что усилено

- **CSRF и сессии.** Для изменяющих cookie-authenticated запросов требуется сессионный CSRF-токен: сервер сравнивает `X-CSRF-Token` и отдельную cookie с токеном сессии, дополнительно проверяются Origin и `Sec-Fetch-Site`. Cookie сессии — `HttpOnly`, `SameSite=Lax`; срок ограничен настройкой. Интеграционные endpoints с отдельным `AGENT_TOKEN` исключены из cookie-CSRF-пути и проверяют собственный секрет.
- **OAuth и администрирование.** Административные API требуют серверную admin-сессию; публичные данные провайдеров не сериализуют credentials. Google OAuth применяет одноразовые state/nonce и PKCE, хранит ограниченный по сроку challenge в SQLite с привязкой к браузерной сессии и атомарным потреблением. ID-токен проверяется через `google-auth`, включая issuer, audience, nonce и подтверждённый email. Секрет admin-кода не выводится в лог.
- **Terminal и подтверждения.** Прямой host fallback выключен по умолчанию; опасные операции ограничены policy/allowlist и требуют подтверждения, таймауты ограничены. Добавлен resource wrapper для дочерних процессов, но это **не контейнерная изоляция**. Проверенные команды `pip install`/`venv` получают ограниченное окно 60–120 секунд; тест проверяет только timeout, реальные установки не запускались.
- **SSRF и web fetch.** URL ограничен HTTP(S), DNS-адреса проверяются на публичную маршрутизируемость, проверки повторяются для redirect; переходы обрабатываются вручную, число redirect и размер ответа ограничены.
- **Данные и медиа.** `knowledge_search` ограничен владельцем; владельцы медиа хранятся в SQLite, а выдача файлов проверяет владельца. Загрузки ограничены фактически прочитанными байтами, нормализуются имена и проверяются сигнатуры; SVG отклоняется. Привязка изображения к чату выполняется атомарно.
- **Задачи и AI-данные.** Claims расписания резервируются атомарно с lease для восстановления после сбоя; media jobs получили TTL/лимит количества и polling locks. Composio требует одноразовое подтверждение. Скрытые reasoning/chain-of-thought данные не выдаются как ответный поток; длина TTS ограничена.
- **Frontend и тестовая среда.** Добавлены базовые security headers, CSRF-клиент, URL-проверки и регрессионные тесты. Тестовый GIF создаётся во временном каталоге. Test-only network guard блокирует внешние DNS/TCP-соединения, разрешая loopback; отдельная временная БД предотвращает использование игнорируемой рабочей базы в тестах.

## Что остаётся риском

- **Идентичность.** Проверенный Google email — более сильный владелец данных, но анонимные данные всё ещё привязаны к подписанному browser/session ID. Это не полноценная аутентификация и не защита от передачи или компрометации cookie. Нет полной модели User/Organization/Role, глобального отзыва сессий и MFA; никнейм не доказывает личность.
- **CSP и браузерная политика.** Базовые headers добавлены, но CSP всё ещё допускает `unsafe-inline`, `unsafe-eval` и широкие HTTPS-источники. Permissions-Policy и origin-specific CORS policy не реализованы; secure cookies/HSTS требуют проверки за реальным TLS reverse proxy и доменом.
- **Файлы.** Есть MIME/signature и size checks, но нет антивирусного hook, пользовательских квот, полной защиты от ZIP-bomb и ограничений распакованного OOXML/PDF-объёма. Старые медиа без записи владельца закрыты (404), пока их безопасно не сопоставят; автоматический backfill не выполнялся.
- **Распределённость.** Владельцы медиа и OAuth challenges хранятся в SQLite, но сами media jobs и часть challenge/confirmation-состояния остаются process-local; файлы зависят от локального/shared filesystem. SQLite и локальные rate limits не гарантируют корректную работу нескольких независимых workers.
- **SSRF TOCTOU.** DNS и redirect проверяются до запроса, но HTTP-клиент повторно разрешает hostname при подключении; остаётся теоретическое окно DNS-rebinding/TOCTOU. Проверка не заменяет egress firewall.
- **Исполнение кода.** Публичное использование terminal небезопасно без отдельного непривилегированного контейнера/VM с ограничениями CPU, RAM, процессов, syscalls, файловой системы и сети. Host execution нельзя включать на публичном сервере.
- **Проверка секретов и CI.** Gitleaks локально недоступен, поэтому текущая рабочая версия не получила локальный secret scan. Workflow добавлен, но GitHub Actions здесь не запускался.

## Миграции, данные и конфигурация

- Миграции аддитивные: добавлены таблицы/индексы `media_file_owners`, `oauth_challenges` и колонки через `CREATE ... IF NOT EXISTS`/проверку наличия. Удаляющих миграций нет. Тесты запускались с отдельным `NOVAMIND_DB_PATH`; данные и историю не удаляли.
- Ранее тестовый импорт приложения затронул локальную игнорируемую `novamind_chats.db`, добавив пустую таблицу и индекс; read-only проверка тогда показала 0 записей в новой таблице. Backup перед тем импортом не делался. Это не удалило историю, но не заменяет backup перед production-миграцией; старые media owners нужно сопоставить контролируемо.
- Возможные breaking changes: admin API требует сессию (401 без неё); `/run` без токена отвечает 503; `/api/composio/execute` сначала возвращает `409 confirmation_required`; незарегистрированные медиа не выдаются.
- Перед production задайте устойчивые `SESSION_SECRET` и `ADMIN_CODE`, проверьте `SITE_URL` и TLS proxy, корректный `GOOGLE_CLIENT_ID` и отдельный `AGENT_TOKEN`, если нужен `/run`. Не включайте host-terminal execution для публичного приложения.

Перед объединением или развёртыванием нужны отдельные решения по полноценной идентичности пользователей, изолированному sandbox, backfill старых медиа и инфраструктуре multi-worker/job storage. До отдельного разрешения пользователя push не выполнять.
